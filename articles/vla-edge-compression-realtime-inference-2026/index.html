    把雲端的大腦塞進機器人：2026 年 VLA 的邊緣壓縮之戰

    前言：訓練在雲端，但控制迴路在機器人身上

    過去兩年，VLA（Vision-Language-Action）基礎模型把「一個模型操作任意機器人」從口號變成 demo。但有件事在 demo 影片裡看不到：那些模型多半是幾十億參數的怪物，跑在桌底下的 GPU 工作站上。OpenVLA 是 7B 參數、在 GPU 上約 5Hz；π0 是 3B、約 10Hz。

    問題是——機器人的控制迴路不在桌底下，它在機器人身上。 一個手臂要平順抓取、一台人形要走路不跌倒，控制命令得以 30–100Hz 的頻率送出，而且算力得塞進機身、功耗壓在個位數瓦特。一個反應要兩秒的策略，在實體世界裡不是「慢」，是「危險」。

    於是 2026 年 VLA 領域真正的主線，不是把模型練得更聰明，而是一個很工程的命題：怎麼把這顆雲端訓出來的大腦，壓進機器人的身體裡，還讓它跑得夠快。 這篇想講清楚這場壓縮戰的兩條攻擊路線，以及一個關鍵的、和聊天機器人完全不同的事實：這裡的壓縮代價是物理的。

    一、先認清瓶頸：這不是「跑得快一點」的問題

    把 VLA 搬上邊緣，卡關的地方和一般 LLM 推論很不一樣。綜述（arXiv:2510.17111）把瓶頸拆得很清楚，我用工程語言重講：

    • 視覺 token 吃掉一切：影像輸入展開後的 token 數，通常主宰整個序列長度，記憶體與算力預算大半耗在這。文字 prompt 反而是小頭。
    • 自迴歸的順序依賴：一個 token 接一個 token 解碼，這種序列依賴是延遲的硬天花板，GPU 再大也救不了單步的關鍵路徑。
    • 重視覺骨幹的記憶體足跡：ViT 級的視覺編碼器加上 LLM 本體，光是權重就放不進邊緣晶片的記憶體。
    • 要的是「有界延遲」，不是「高吞吐」：這點最容易被忽略。控制迴路要的是每一步都在期限內回來，而不是平均很快、偶爾卡頓。一次 200ms 的尾延遲，可能就是手臂撞上桌角。

    換句話說，目標函數和雲端推論根本不同：雲端優化平均吞吐量，邊緣控制優化的是最壞情況延遲的上界。這個差異會貫穿後面所有設計選擇。

    二、第一條路線：把模型本身變小變便宜

    最直觀的攻擊——直接縮模型。2026 年這條線已經卷到極致：

    量化：從 INT8 一路殺到 1-bit

    • BitVLA 把 VLA 推到 1-bit，記憶體從 15.1GB 壓到 1.4GB（約 11 倍），端到端延遲降約 4.4 倍，而且宣稱效能仍貼齊全精度基線。這在一年前會被當成天方夜譚。
    • LiteVLA-Edge 走比較務實的 4-bit 訓練後量化（PTQ），在 Jetson Orin 級硬體上完全離線跑出約 150.5ms（~6.6Hz）的端到端延遲。
    • DyQ-VLA 更聰明：用「敏感度感知的位寬切換」搭配「運動學引導的位元分配」，只用 30.9% 記憶體就保住 99.5% 的基線效能，實機任務加速最高 1.43 倍。

    DyQ-VLA 的思路值得標起來——不是所有層都該用同一個位寬。對動作精度敏感的層保留高位寬，其餘狠狠壓。這和我做感知時的直覺一致：壓縮不該是均勻的，該跟著「哪裡出錯代價最大」走。

    蒸餾與輕量骨幹：換掉怪物本體

    另一條是直接換小骨幹或把大模型蒸餾成學生模型：RoboMamba（2.7B）、TinyVLA（1.3B）、SmolVLA（0.24–2.25B）這類「天生瘦」的架構，配上 CEED-VLA、VITA-VLA 這類蒸餾方法，把大模型的能力灌進小模型。

    Token 剪枝：別讓視覺 token 拖垮一切

    既然視覺 token 是大頭，那就動態剪掉不重要的：FastV、LightVLA、FlashVLA、SpecPrune-VLA 這一票方法，本質都是「這一幀裡哪些 patch 對當前動作沒貢獻，直接丟」。配合 KV-cache 跨幀重用（VLA-cache），把連續幀之間沒變的部分省下來。

    三、第二條路線：不縮模型，改「什麼時候跑、怎麼跑」

    第二條路線更巧——承認模型就是慢，那就重構推論的時序，把延遲藏起來。

    Action Chunking：一次吐一串動作

    核心招式是 action chunking：策略一次吐出 8–50 個未來動作的「chunk」，機器人開迴路執行這串動作的同時，背景計算下一個 chunk。等於把昂貴的推論頻率攤平——模型其實只在每串開頭推論一次，但機器人感受到的是連續平順的命令流。

    System 1 / System 2 非同步架構

    更進一步是雙系統設計：大模型當「慢思考」的高層規劃（System 2），小策略當「快反射」的執行器（System 1），兩者非同步跑。System 1 用 diffusion 或 flow-matching head 以 30–100Hz 直接閉合感知-動作迴路，System 2 在背景慢慢想。

    2026 年這條線的代表作 VLASH（未來狀態感知的非同步推論）宣稱在不改架構、不加額外開銷下，速度提升最高 2.03 倍、反應延遲降低最高 17.4 倍，且完全保留原始精度。

    四、誠實的取捨：action chunking 藏起了延遲，但也藏起了世界的變化

    這是全文我最想講的一段，也是論文裡最容易被漂亮數字蓋過去的張力。

    Action chunking 之所以快，是因為機器人在開迴路執行一串基於「過去某一刻觀測」算出來的動作。但實體世界不會等你——chunk 執行到一半，旁邊的人伸手進來了、要抓的杯子被碰倒了，而機器人手上那串動作是對著一個已經過期的世界算的。

    所以 chunk 越長，吞吐越漂亮，反應性越差。這不是 bug，是 chunking 的本質定價。2026 年一整批工作（Real-Time Chunking、Leave No Observation Behind、Masked Action Chunking）本質都在解同一道題：怎麼在享受 chunk 平順度的同時，讓新觀測還能即時修正手上這串動作。 答案大多是「邊執行邊用最新觀測軟性覆寫 chunk 尾段」。

    更深一層的取捨在量化這端。聊天機器人量化掉一點精度，最糟是答案文謅謅、偶爾幻覺，使用者皺個眉。但VLA 量化掉的精度會變成實體後果——夾爪偏移幾毫米就抓空、力道判斷錯一點就捏碎或撞壞。綜述用了一個很精準的詞：aggressive compression 威脅的是「執行期的物理可靠性」（physical reliability），這是 embodied 系統獨有、純 VLM 沒有的風險維度。

    所以邊緣 VLA 真正的設計問題，從來不是「壓到多小」，而是：在不犧牲物理可靠性的前提下，能壓到多小、藏掉多少延遲。 這跟我先前寫過的「部署時可靠性」是同一套世界觀——承認模型不完美，問題是出錯時代價有多大、能不能兜住。

    五、對嵌入式 / 邊緣工程師的幾個 takeaway

    1. 優化目標是尾延遲，不是平均吞吐。 控制迴路吃的是最壞情況的上界。benchmark 時別只看 mean latency，盯 p99；一次尾延遲在實體世界可能就是一次碰撞。
    2. 壓縮要非均勻、跟著代價走。 DyQ-VLA 的位寬切換、token 剪枝的選擇性丟棄，背後都是同一個原則：把預算花在出錯代價最大的地方。這對做感知壓縮的人完全可遷移。
    3. 時序重構和模型壓縮是正交的兩把刀，要一起用。 量化把模型塞進記憶體，chunking / 非同步把延遲藏進執行縫隙。單靠一條都不夠，30–100Hz 個位數瓦特這個目標需要兩條一起上。
    4. chunk 長度是個安全旋鈕，不只是效能旋鈕。 調長 chunk 換來平順與低算力，但你在拿反應性換。在有人在旁邊的場景，這個旋鈕該往「短」的方向轉。
    5. 硬體目標很具體：Jetson Thor / Orin、Qualcomm RB6、自研晶片，個位數瓦特。設計時心裡要有那塊晶片的記憶體與功耗預算，而不是先做完再想怎麼塞。

    結語：壓縮戰的下一步

    2026 年的 VLA 邊緣化已經從「能不能跑」進到「跑得夠不夠穩、夠不夠安全」。1-bit 量化證明了模型可以瘦到不可思議，非同步架構證明了延遲可以藏得很深。但這兩條路線越激進，那個物理可靠性的紅線就越需要被認真對待。

    我的判斷是：下一個真正的突破點不在「更小的模型」或「更快的推論」，而在讓壓縮與時序重構變成可驗證、有保證的——能對使用者說「這顆壓到 4-bit 的策略，在這個功耗預算下，最壞延遲不超過 X、物理失效率不高於 Y」。在那之前，邊緣 VLA 的每一次壓縮，都還是一場拿可靠性下注的工程賭局。
